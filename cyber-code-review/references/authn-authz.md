# Area 2: Authentication and authorization

Use this checklist for every changed authentication path, session path, permission check, and data access. For a diff that touches none of these, mark the area not applicable, with the list of files you checked and the reason.

Tags: `[S]` sourced. `[O]` originated; anchor given or "no anchor". Regression rule: a removed check is covered by SKILL.md step 5 and is not repeated here.

## Authentication

**AA-1 [S] No default or built-in credentials.** Default accounts (for example root, admin, sa) are absent or disabled. Credentials for service authentication are not default values.
- *Look for:* seeded users, default passwords in migrations or fixtures that run outside tests, service accounts with the vendor default password.
- *Source:* ASVS 5.0 6.3.2; ASVS 5.0 13.2.3 (service credentials are not default values).

**AA-2 [S] Password comparison and handling.** A changed password check compares values in constant time and verifies the password exactly as received, without truncation, trimming, or case folding.
- *Look for:* `==` on hashes or tokens instead of a constant-time compare; `password[:N]`, `.lower()`, or `.strip()` applied to the password before hashing or verifying.
- *Source:* ASVS 5.0 6.2.8 (no modification of the password before verification); OWASP-AUTHN, "compare password hashes using safe functions".

**AA-3 [S] Brute-force and credential-stuffing controls.** A new or changed login, reset, or code-entry endpoint has throttling or lockout with thresholds the documentation sets, and lockout events are logged.
- *Look for:* a new login route with no rate limit or lockout; a changed limiter that counts only successful attempts.
- *Source:* ASVS 5.0 6.3.1; OWASP-AUTHN, Account protection item (lockout with appropriate thresholds).

**AA-4 [S] No user enumeration.** Responses to login, registration, and reset are the same for existing and non-existing accounts, in status, body, and timing as far as the code controls.
- *Look for:* error messages that say "user not found" versus "wrong password"; a registration response that says the email is taken.
- *Source:* OWASP-AUTHN, "Authentication and Error Messages" section (generic responses). No ASVS anchor verified in this survey.

**AA-5 [S] Initial and activation secrets.** System-generated initial passwords and activation codes come from a secure random source, follow the password policy, and expire after a short time or first use.
- *Look for:* activation codes built from timestamps, sequential IDs, or a non-cryptographic random source; codes with no expiry.
- *Source:* ASVS 5.0 6.4.1; ASVS 5.0 11.5.1 for the random source (see cryptography.md CR-7).

**AA-6 [S] Session tokens.** Reference session tokens are generated by a CSPRNG and carry at least 128 bits of entropy. UUIDs are not sufficient.
- *Look for:* session IDs from a non-cryptographic generator, from `uuid4` alone, or from a time-based value.
- *Source:* ASVS 5.0 7.2.3; OWASP-AUTHN, Session management item (token generation with 128 bits of entropy or more).

**AA-7 [S] Session lifecycle.** A new session token is issued on login and on re-authentication, and the previous token is ended. Logout, expiry, and account disablement stop further use of the session, and all sessions end when an account is disabled or deleted.
- *Look for:* a login that keeps the pre-login session ID; a logout that clears the client cookie but leaves the server session valid; account disablement that leaves sessions active.
- *Source:* ASVS 5.0 7.2.4 (new token on authentication); ASVS 5.0 7.4.1 (termination disallows further use); ASVS 5.0 7.4.2 (all sessions end on disable or delete); OWASP-AUTHN, Session lifecycle item (invalidation on logout and timeout).

**AA-8 [S] Session cookie attributes.** Session cookies set HttpOnly, Secure, and an appropriate SameSite value.
- *Look for:* a new `Set-Cookie` or cookie helper that omits one of the three attributes; a changed attribute that weakens an existing one.
- *Source:* OWASP-AUTHN, Session security item (cookie attributes). No ASVS anchor verified in this survey.

**AA-9 [S] Re-authentication for sensitive operations.** Changing a password, email, MFA setting, payout details, or similar, and deleting an account, requires re-authentication or a recent-authentication check.
- *Look for:* a sensitive change endpoint that checks only the session, not a recent login or a current credential.
- *Source:* OWASP-AUTHN, Re-authentication item (sensitive operations). No ASVS anchor verified in this survey.

**AA-10 [O] Session path trace.** For a changed session path, trace the session from issue, through use and renewal, to revocation, and check each transition against AA-7. A transition with no code path is a candidate finding.
- *Look for:* a token refresh path that issues a new token but never revokes the old one; a revocation list that is written but never read on the request path.
- *Source:* anchored to ASVS 5.0 7.2.4, 7.4.1, and 7.4.2. The step-by-step trace is originated.

## Authorization

**AA-11 [S] Deny by default.** A new route, handler, or action is denied unless an explicit permission grants it.
- *Look for:* a new route with no decorator, guard, or middleware, in a framework where the default is to allow; a permission table that falls back to allow for unknown roles.
- *Source:* OWASP-AUTHZ, "deny by default"; ASVS 5.0 8.2.1 (function-level access restricted to explicit permissions).

**AA-12 [S] Authorization on every request.** The permission check runs on every request to the protected operation, including in internal handlers, batch jobs, and alternate routes to the same operation.
- *Look for:* a check added to the UI route only, while the API route, a websocket, or a background task reaches the same operation.
- *Source:* OWASP-AUTHZ, "validate the permissions on every request"; ASVS 5.0 8.3.1 (enforced at a trusted service layer).

**AA-13 [S] Server-side enforcement.** Access control is enforced on the server. Client-side checks are never the control.
- *Look for:* a permission flag returned to the client and trusted on a later server call; a hidden field or a client-set role.
- *Source:* OWASP-AUTHZ, section on where authorization checks belong (never client-side); ASVS 5.0 8.3.1.

**AA-14 [S] Object-level authorization (IDOR and BOLA).** Each lookup by ID checks that the caller owns the object or has a grant for it. Guessed or tampered IDs do not grant access.
- *Look for:* `get_by_id(request.id)` with no ownership filter; object references in a changed body or query that are trusted without a scope check.
- *Source:* ASVS 5.0 8.2.2 (data-specific access, IDOR and BOLA); OWASP-AUTHZ, "lookup IDs are not accessible even when guessed or cannot be tampered with"; OWASP-SCR, Authorization checklist, "IDOR prevention".

**AA-15 [S] Authorization after authentication.** Authorization is checked after authentication is confirmed, and it is not skipped by an early return in the middle of the flow.
- *Look for:* an early return on a success path that bypasses the later permission check; a middleware ordering change that places a permission check before authentication.
- *Source:* OWASP-SCR, Authorization checklist (post-authentication checks).

**AA-16 [S] Failed authorization exits safely.** Any failed or erroring permission check ends the request with a denial. The code does not fall through to the operation.
- *Look for:* `try: check() except: pass`; a permission function that returns None on error and the caller treats None as allowed.
- *Source:* OWASP-AUTHZ, "exit safely when authorization checks fail"; ASVS 5.0 16.5.3 (no fail-open behaviour).

**AA-17 [S] Response data minimisation.** A changed endpoint returns only the fields the caller needs. Serialising a whole object into a response, including internal fields, credentials, or other users' data, is a finding.
- *Look for:* a serialiser that uses all model fields; a changed response that adds a field such as a hash, token, internal ID, or email of another user.
- *Source:* ASVS 5.0 15.3.1 (only the required subset of fields returned).

**AA-18 [S] Subject-based access at higher assurance.** At L3 scope, access to an object is decided by the originating user's permissions, not the permissions of an intermediary service acting on their behalf. Apply this item only when the project targets L3.
- *Look for:* a background job or service account that performs a user-triggered read or write with its own broader permissions and no check of the user's rights.
- *Source:* ASVS 5.0 8.3.3 (L3).

**AA-19 [O] Privilege change paths.** A changed path that assigns, grants, or elevates a role, scope, or group checks that the actor is allowed to do so, and that the target is in scope.
- *Look for:* a role-update endpoint that accepts a role the actor could not grant; an invitation flow that lets an invitee choose their own role.
- *Source:* anchored to ASVS 5.0 8.2.1 and 8.2.2. The privilege-change check is originated.
